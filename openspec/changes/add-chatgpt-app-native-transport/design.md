## Context

MDB currently exposes `chatgpt_conversation_start`, but its raw same-origin `fetch` to ChatGPT's private conversation endpoint receives HTTP 403 because the first-party web application generates short-lived request proof at submission time. A signed-in background ChatGPT tab already has the required browser state and first-party submission code. MDB can invoke a validated internal runtime action through its existing fixed-function Chrome boundary without exporting credentials, automating visible controls, or allowing arbitrary page script execution.

## Goals / Non-Goals

**Goals:**

- Make runtime-native submission the default transport for the existing MCP tool and loopback HTTP endpoint.
- Keep the ChatGPT tab in MDB's background lease pool without foregrounding it.
- Capture only the response body and stable response metadata needed to normalize the result.
- Detect successful submission, bounded completion, and ambiguous handoff states.
- Preserve prompt redaction and existing request/runtime/output limits.

**Non-Goals:**

- Capture, replay, solve, or return request authorization or anti-abuse headers.
- Expose arbitrary JavaScript or selector execution to MCP callers.
- Emulate the OpenAI Responses API or preserve Codex tool-call continuations.
- Automatically retry after the page may have submitted a prompt.
- Type into, click, or otherwise automate the visible ChatGPT composer.

## Decisions

### Discover and invoke a fixed first-party runtime contract

The Chrome extension will expose a fixed `tabs.chatgptRuntimeConversationStart` method. A read-only inventory step will identify the current module/chunk and callable action that ChatGPT itself uses to start a conversation. The production method will accept only the bounded prompt and model selection, resolve the action through fixed fingerprints, validate its shape, and invoke it. Caller-provided module identifiers, property paths, selectors, scripts, URLs, headers, and request bodies are not accepted.

Alternative considered: continue adding private endpoint headers. Rejected because those values are session-bound, short-lived, security-sensitive, and generated by first-party code.

Alternative considered: fill and submit the composer. Rejected because it is UI automation and does not provide a meaningful internal transport boundary.

### Observe response bodies without observing request secrets

Immediately before submission, a fixed main-world observer will wrap `window.fetch` only long enough to clone successful or failed responses whose URL path matches ChatGPT's conversation endpoint. It will parse the cloned response using the existing bounded SSE normalization logic while returning the untouched original response to the page. The observer will not inspect fetch request headers, cookies, tokens, proof values, or unrelated traffic, and it will restore the original function when the operation finishes.

A bounded DOM fallback may read the latest assistant message and conversation URL if ChatGPT changes its response transport but renders a stable result. It must not scrape account/session data.

### Use an operation identifier and terminal ambiguity state

Each app-native call receives an internal operation identifier. The page stores bounded observer state under that identifier so subsequent fixed polling calls can retrieve progress. If the send action occurred but completion cannot be established, MDB returns `CHATGPT_CONVERSATION_HANDOFF_UNCERTAIN` with any observed conversation identifier and never resubmits automatically.

### Keep transport selection explicit and backward compatible

`transport` accepts `runtime` or `raw`; omitted values default to `runtime`. The `raw` mode remains a diagnostic probe for protocol research and retains its fail-closed proof classification. `auto` is deliberately excluded because falling back after a runtime submit could duplicate a conversation.

### Keep the page backgrounded and restore it safely

The operation uses the existing workspace lease lifecycle and never activates the tab or window. It may navigate an eligible leased tab to a new-chat URL when needed. Cleanup releases the lease and observer state without closing or foregrounding a user-owned tab.

## Risks / Trade-offs

- [ChatGPT bundle/module changes] -> Resolve only fixed fingerprints discovered by the bounded inventory and return a classified runtime-changed error before invoking anything.
- [Fetch transport changes] -> Use bounded DOM and conversation-URL observation as a secondary result source; classify incomplete results rather than retrying.
- [Observer affects page fetch behavior] -> Preserve call arguments and the original response, clone only matching responses, restore promptly, and cover behavior with tests.
- [Prompt submitted but response polling times out] -> Return terminal handoff uncertainty with available identifiers so the caller can inspect the conversation manually.
- [Background throttling increases latency] -> Use the existing extended native-host timeout and bounded polling interval; never activate the tab as a workaround.
- [Private frontend runtime contracts are inherently unstable] -> Keep the endpoint experimental, version the fingerprint, and retain the raw diagnostic mode for investigation only.

## Migration Plan

1. Add the fixed Chrome runtime inventory and invocation methods with unit coverage.
2. Route omitted transport values to `runtime` while retaining explicit `raw` behavior.
3. Reload the unpacked extension and restart MDB.
4. Run one harmless signed-in live prompt and verify prompt redaction, background behavior, and normalized output.
5. Roll back by restoring the default transport to `raw` or reverting the change; no credentials or database migrations are created.

## Open Questions

- None for the current August 25, 2026 runtime fingerprint. Runtime drift remains an expected classified failure; DOM submission automation is not an allowed fallback.

## Verification Outcome

- The mounted ChatGPT runtime exposed exactly one shared composer-store `submitComposer` action with an explicit `{ accepted, completion }` result.
- Invoking `submitComposer(new Event("submit"), { kind: "text_action", text: prompt })` generated the first-party conversation request and its browser requirements without UI typing/clicking or credential/proof extraction.
- The live loopback endpoint returned HTTP 200, `Cache-Control: no-store`, `complete: true`, a conversation identifier, an assistant message identifier, and the exact assistant text `MDB_HTTP_RUNTIME_OK` while `tab_active` remained false.
- The full MDB test suite and strict OpenSpec validation passed.
